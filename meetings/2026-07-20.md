    * Battery pack notes:  
      * Battery packs intended to help bridge common challenge, “how do I find/recommend libraries that I ought to be using”.  
      * Crate with name like “embedded-battery-pack”, not intended to be directly used but rather a template that helps you add to your project  
      * Demo showing \`embedded-battery-pack\` based on awesome-embedded-rust project  
        * [https://crates.io/crates/embedded-battery-pack](https://crates.io/crates/embedded-battery-pack)  
      * Intentionally resolves as just regular dependencies in your Cargo.toml, it is a guide to the [crates.io](http://crates.io) ecosystem, not a replacement  
        * Also some aren’t dependency related at all \- [https://crates.io/crates/ci-battery-pack](https://crates.io/crates/ci-battery-pack)  
    * Presentation’s goal today is not to sell on battery packs, but rather a problem, which battery packs might be part of a solution, and RCN might be interested in participating  
      * Crates are not really discoverable, hard to know what is best to use  
      * [blessed.rs](http://blessed.rs) is helpful, but it is just a website, not quite as accessible, also discoverability problem  
      * Actually knowing which crates to use is only half the battle: if you are building something out that you want prod reliance on, you want funded maintenance \+ ability to upstream a fix  
        * Ideally not funded by one company, both to avoid undue influence \+ for sustainability  
        * Security is a big reason  
          * Probably rust unsafe is going to be a target once people finish on C++ memory  
          * The way to upstream fixes will need to change since people can scrape vulnerability fixes \= effective 0-day  
        * Not only about just having funded maintenance in general, but also sustainable maintenance with more than one author, succession planning, etc  
      * Related problems: who owns interop? You want competing solutions, but consumers should be able to rely on interfaces to build across approaches  
        * Example: hardware abstraction layers from Embedded Working Group  
      * Want to make it easy to find suggestions for what to use, what works well with them, and also have a good way for companies to put money into those dependency sets  
        * This gives us a beneficial cycle, where company tries rust, has more success, start to sponsor rust, rust and crates get better, etc  
    * Discussion (is this a real problem? How can we sell this to companies to give $$? What role should RCN play?)  
      * I think what is described here is a "meta-framework" from other programming languages/stacks (eg "Rails" for Ruby and things like that), please correct me if I am wrong here  
      * This is a major barrier to adoption in enterprise, ecosystem is challenging, battery packs might be helpful to close that gap  
      * we have built [https://gerust.rs](https://gerust.rs) a while ago, similar spirit – didn't get much attention though and since stalled  
      * Risk of unfair advantage, this crate is backed by working group, so newcomers have trouble  
        * Useful to use BP to define interfaces that make it easier to swap things out between frameworks, can add “experimental” ones  
        * Not necessarily a bad thing to have one big crate that most people use, it’s a way to pool resources, to contribute to a central effort  
        * Battery packs are nice way to capture trade offs between different approaches  
        * BP maintainers are going to be interested in the latest and greatest option so are likely to be dynamic with inclusion  
      * [batterypack.rs](http://batterypack.rs) website would super helpful for newcomers to get off the ground  
        * Historically rust doesn’t have huge meta-frameworks like ruby on rails, rust is more modular, so it’s nice to let consumers choose their pack themselves  
      * Downside is that you might need to migrate to a battery pack to benefit from that nicer story, that’s one cost of adoption potentially  
        * Ideally the bp reflects what people are using already so not a huge migration burden  
      * BPs have an additional feature of defending against supply chain attacks in terms of guaranteeing support guarantees for CI best practices and so forth  
        * I was thinking if the RCN will provide any SLA on bug/cve fixes for BP. Any benefit from using BP vs just picking the same crates on my side? I saw some discussion about LTS. Does that applies to BP?  
        * “We guarantee there is a paid maintainer for crates in this battery pack”?  
        * Foundation: “These 7 battery packs are foundation supported”?  
    * What role should RCN play?  
      * This is a great outcome for RCN initiatives \- having a battery pack  
        * Useful to centralize in initiatives to avoid fragmentation of battery packs themselves (many embedded bps)	  
        * Very valuable to not have any one group maintaining their set of crates, a lot of value in pooling maintenance/funding  
      * Can we make the slides from this talk public? Especially the virtuous cycle one?  
        * [https://nikomatsakis.github.io/rcn-july-2026/](https://nikomatsakis.github.io/rcn-july-2026/)  
      * IMO batterypack is most interesting not as a tool, but as an idea of RCN-endorsed "here is where well supported ecosystem at" that also happens to have a tool  
      * Could have foundation-oriented ecosystem fund/sponsor group that have a set of crates that they are directing funding to, and the role of the RCN to provide recommendations for what should go in there, and perhaps to maintain battery packs based on those  
      * Next steps?
